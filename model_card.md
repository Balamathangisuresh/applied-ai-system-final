# 🕵️ Model Card: Mystery & Mayhem

## 1. Model Name

Mystery & Mayhem

---

## 2. Intended Use

Describe what your AI agent is designed to do and who it is for.

Prompts:

- What does it generate (clues, hints, coaching)
- What assumptions does it make about the game state
- Is this for real users or classroom exploration

It generates two things inside a Streamlit number-guessing game: progressive detective-style clues about a hidden secret number in Detective Mystery mode, and a short end-of-game coaching paragraph summarizing performance stats in either mode. It assumes it's only ever asked about a secret already generated by the game, that the caller has already computed which facts are true and unrevealed (it never invents facts on its own), and that the coaching call receives real, honestly-computed stats rather than made-up numbers. This is a classroom exploration of agentic-workflow and reliability patterns for an applied AI course, not a production feature — there's no persistence across sessions and no real user accounts behind it.

---

## 3. How the Model Works

Explain your agentic workflow in simple language.

Prompts:

- What does the "Analyze" step look like
- What "tools" does it call and what do they check
- How does Claude get involved, and what is it actually allowed to decide
- What changes did you make from the starter logic

Every wrong Detective guess follows the same three-step pattern: Analyze, Tool Call, Refine & Output. Analyze: Python looks at which clue "facts" about the secret (even/odd, prime, divisible by 3, digit sum, etc.) haven't been shown yet. Tool Call: Python runs the actual fact-check functions against the secret itself, so the list handed forward is already verified true, not guessed. Refine & Output: exactly one Claude call gets that verified list and is only allowed to pick one `fact_key` from it — enforced by a JSON-schema `enum`, not just a prompt instruction — and phrase it as a themed clue. Claude never decides what's true about the secret, only how to word an already-true fact. The end-of-game AI Coach works the same way but simpler: real stats go in, one call comes back with 2-3 sentences, no schema constraint since there's no secret left to leak by that point. Both calls are wrapped in validation, and if anything looks off — a disallowed fact, the literal secret appearing in the text, an empty or malformed response, a missing API key, a timeout — the code falls back to a canned, tested template instead of showing anything unverified. The starter project (Module 1) had no AI generation at all, just a static "Higher/Lower" string; this whole agentic + reliability layer is new, built on top of that fixed core.

## 4. Data

Describe the data the agent's decisions are built on.

Prompts:

- What facts/config drive the clues and damage
- What ranges or tiers are represented
- Did you add or remove anything from the starter
- What's missing or thin

There's no external dataset here — the "data" is a small hand-written fact registry (10 fact types: `is_even`, `is_odd`, `is_prime`, `is_perfect_square`, `upper_half`, `lower_half`, `divisible_by_3`, `divisible_by_4`, `digit_sum`, `digit_count`) and three tier configs per mode (Detective: Rookie/Detective/Master Case, ranges 1–30 to 1–150; Boss Fight: Goblin/Knight/Dragon, ranges 1–20 to 1–100, 50–120 HP). None of this existed in the starter project, which had one flat difficulty-to-range mapping and no clue system at all.

Ten fact types is thin for the higher-attempt tiers: a real playthrough against the number 12 in an 8-attempt round only produced 5 distinct true facts before the game had to fall back to "No more clues available" for the remaining attempts (see Section 10). There's also no fact type based on proximity to round numbers or to the range's midpoint beyond the single upper/lower-half split, so clues can feel repetitive across games with a similarly-shaped secret.

## 5. Strengths

Where does the system seem to work well?

Prompts:

- Cases where it behaves reliably
- Patterns the reliability layer captures correctly
- Where behavior matched your intuition

It never leaks the secret, never repeats a fact within a game, and never crashes — confirmed by 54 passing pytest tests plus a full Streamlit playthrough with no API key configured at all (see Section 10), which is exactly the scenario a grader running this without setting up billing would actually hit. The higher/lower hint is shared identically between Detective Mystery and Boss Fight, so the core "am I getting warmer" feedback is consistent no matter which mode you're in. The fixed damage bands (0 / 1 / 5 / 10 / 20 by distance) make Boss Fight combat legible at a glance — a player can tell from the number alone how close they were, without ever seeing the actual secret.

## 6. Limitations and Bias

Where the system struggles.

Prompts:

- Cases it doesn't handle well
- Where the fallback shows its seams
- Anything that overfits to one path
- Ways the design might unintentionally favor certain play styles

With only 10 fact types, any tier with more than about 6–7 attempts per round will exhaust real clues before the round ends, and the game repeats the same generic "trust your deductions" line for every attempt after that — a real playthrough hit this by attempt 6 of 8 (Section 10). The AI Coach's fallback text is bucketed into only three efficiency tiers (≥80%, 50–79%, <50%), so two fairly different performances — 79% vs. 51% efficiency — get the exact same sentence. The boss-fight damage bands are fixed absolute distances (off-by-1, off-by-2, off-by-5) rather than scaled to each tier's range, so Dragon (range 1–100) is quietly much harder to land a critical hit against than Goblin (range 1–20) — that asymmetry was a deliberate simplification, not something actually playtested for balance. And because no `ANTHROPIC_API_KEY` was ever configured during development, every clue and coach line observed and tested here was the deterministic fallback path — real Claude phrasing was only ever verified structurally, via mocked responses in `test_ai_agent.py`, never actually read.

## 7. Evaluation

How you checked whether the agent behaved as expected.

Prompts:

- What you tested and how
- What surprised you
- Any tools or harnesses you used

54 pytest tests split along the code's own boundary: `test_game_logic.py` covers every pure function (tier configs, `parse_guess`/`check_guess`, the boss damage bands, the fact registry, the stats math) with no mocking, and `test_ai_agent.py` mocks the Claude client at the exact call site and separately tests the happy path and every fallback trigger — no API key, a raised exception, a disallowed `fact_key`, a leaked secret, malformed JSON, and an exhausted clue pool (asserted to never even attempt a call). Since there was no way to click through an actual browser in this environment, the full app was also driven end-to-end with Streamlit's `AppTest` harness — real playthroughs of wins and losses in both modes, asserted against session state, not just eyeballed.

The real surprise was that the harness-driven testing caught bugs the pure-logic tests never could, because they were about *when* something renders, not what it computes: the Submit button sometimes needing two clicks, the attempts-left/HP display showing the previous guess's numbers instead of the current one, and an invalid guess wrongly costing an attempt. All three passed every logic test while still being live bugs in the actual app.

## 8. Future Work

Ideas for improving the agent next.

Prompts:

- Additional clue types or coaching nuance
- Better validation or scaling
- Things you'd want to actually observe with a real API key


- Scale the boss-fight damage bands to each tier's range instead of using the same fixed distances for Goblin and Dragon alike.
- Give the AI Coach more than three efficiency brackets, or let Claude vary its tone/persona for replay variety.
- Track stats across sessions so the coach could compare a run to the player's own history, not just this one game.

## 9. Personal Reflection

A few sentences about your experience.

Prompts:

- What you learned about building reliable AI features
- Something unexpected you discovered
- How this changed how you think about integrating AI into an app

- Building the reliability layer taught me that most of what makes an AI feature feel trustworthy has almost nothing to do with the model call itself — it's the validation and fallback wrapped around it. The actual "AI" part of `generate_detective_clue` is a few lines; the rest exists to make sure a bad response never reaches the player.
- The most unexpected discovery was that the app's real bugs at this stage weren't in the AI code at all — they were Streamlit render-order issues (a stale attempts count, a submit button needing two clicks) that only showed up once I drove the app end-to-end instead of just unit-testing the logic underneath it.
- This changed how I think about testing AI features: testing the happy path is the easy part; testing what happens when the model call fails, times out, or hallucinates is what actually determines whether a feature is safe to ship, and it's exactly what gets skipped if you only test the "normal" case.
